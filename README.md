# Мини-CRM «Объекты и задачи»

Учёт строительных объектов и задач для двух ролей: постановщик и исполнитель.
Правила доступа и статусов проверяет база данных, поэтому они действуют и при прямых запросах к Supabase в обход интерфейса.

**Стек:** Vite, React, TypeScript, Supabase, supabase-js, React Router, TanStack Query, zod, Mantine.

**Другие документы:**

- [docs/DECISIONS.md](docs/DECISIONS.md): решения там, где ТЗ не даёт ответа, и что не сделано
- [docs/EXPLAIN_FOR_MANAGER.md](docs/EXPLAIN_FOR_MANAGER.md): описание без технических терминов

## Запуск

Нужен Node.js 22.12 или новее и бесплатный проект Supabase. Используйте отдельный проект: миграции забирают права в схеме `public` у ролей `anon` и `authenticated`.

### 1. Закрыть регистрацию

Supabase Dashboard → **Authentication → Sign In / Providers** → выключить **Allow new users to sign up**.

`npm run check:security` проверяет, что регистрация действительно закрыта.

### 2. Создать тестовых пользователей

**Authentication → Users → Add user → Create new user**, с включённым **Auto Confirm User**:

| Email | Роль (её назначит `seed.sql`) | Имя в интерфейсе |
|---|---|---|
| `manager@example.com` | Постановщик | Ирина Постановщик |
| `executor.a@example.com` | Исполнитель | Алексей Исполнитель |
| `executor.b@example.com` | Исполнитель | Борис Исполнитель |

Пароли задаёте вы. В репозитории их нет.

### 3. Применить миграции и демо-данные

В **SQL Editor** выполнить файлы строго по порядку, каждый отдельным запуском:

1. `supabase/migrations/20261104100000_schema.sql`: типы и таблицы
2. `supabase/migrations/20261104100100_functions.sql`: функции и триггеры
3. `supabase/migrations/20261104100200_rls_and_grants.sql`: права и политики
4. `supabase/migrations/20261105100000_allow_executor_change_any_status.sql`: смена исполнителя в любом статусе
5. `supabase/seed.sql`: 3 профиля, 3 объекта, 7 задач с историей

Если первые миграции уже применены, достаточно выполнить новый файл из пункта 4.

`seed.sql` сам находит пользователей по email, копировать UUID не нужно. Повторный запуск ничего не меняет и не удаляет.

### 4. Настроить и запустить приложение

```bash
cp .env.example .env.local
npm install
npm run dev
```

В `.env.local` укажите значения из **Project Settings → API**:

| Переменная | Что указать |
|---|---|
| `VITE_SUPABASE_URL` | Project URL |
| `VITE_SUPABASE_ANON_KEY` | Ключ `anon` или `publishable` |

Секретный ключ (`service_role`, `sb_secret_`) нигде указывать не нужно. Приложение откажется запускаться с ключом `sb_secret_`. Файлы `.env*`, кроме `.env.example`, не попадают в git.

## Экраны

1. Вход по email и паролю.
2. Список объектов. Исполнитель видит только объекты со своими задачами.
3. Карточка объекта и его задачи со статусами. Исполнитель видит только свои задачи.
4. Карточка задачи: данные, кнопки только тех действий, которые доступны этому пользователю в этом статусе, история.
5. «Мои задачи» для исполнителя.

## Статусы

| Переход | Кто | Комментарий |
|---|---|---|
| — → Новая | Постановщик, при создании | Нет |
| Новая → В работе | Назначенный исполнитель | Необязателен |
| В работе → На проверке | Назначенный исполнитель | Необязателен |
| На проверке → Принята | Постановщик | Необязателен |
| На проверке → На доработке | Постановщик | **Обязателен** |
| На доработке → В работе | Назначенный исполнитель | Необязателен |

Все остальные переходы база отклоняет.

Постановщик может сменить исполнителя в любой момент и в любом статусе. Статус при этом не меняется, и запись в историю не добавляется. В принятой задаче больше ничего менять нельзя.

Удалённая задача и её история не видны никому через API и интерфейс, но физически остаются в базе: см. [docs/DECISIONS.md](docs/DECISIONS.md).

## Деплой на Vercel

1. Создайте проект в Vercel: импортируйте репозиторий или выполните `npx vercel` в папке проекта.
2. Настройки сборки Vercel определит сам: Framework **Vite**, Build Command `npm run build`, Output Directory `dist`.
3. В **Project Settings → Environment Variables** добавьте только `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`. Переменные `CHECK_*` и секретные ключи туда добавлять нельзя.
4. Запустите деплой. Vite встраивает эти значения при сборке, поэтому после их изменения нужен новый деплой.

Файл `vercel.json` нужен для прямых ссылок: без него обновление страницы `/tasks/...` вернёт 404.

## Проверка защиты

```bash
npm run check:security              # показать результат
npm run check:security -- --readme  # и записать таблицу в этот файл
```

Скрипт работает как злоумышленник: шлёт прямые запросы через supabase-js с публичным ключом, без интерфейса. Он входит тремя тестовыми пользователями, поэтому в `.env.local` нужно заполнить `CHECK_*_EMAIL` и `CHECK_*_PASSWORD`. Без префикса `VITE_` они не попадают в сборку приложения.

Код выхода: `0` если всё пройдено, `1` если есть проваленные проверки, `2` если проверку не удалось запустить или она прервалась.

**Что остаётся в базе после запуска:**

- созданные скриптом задачи, мягко удалённые: физически удалить их нельзя;
- один объект `[security-check] служебный объект`, который виден постановщику. Он нужен для проверки «объект с удалёнными задачами удалить нельзя», поэтому сам удалён быть не может. При следующем запуске он используется повторно.

Чтобы убрать эти данные перед показом, выполните в SQL Editor от имени администратора. Через API это невозможно:

```sql
begin;
delete from task_history where task_id in (
  select t.id from tasks t join objects o on o.id = t.object_id
  where o.name = '[security-check] служебный объект'
);
delete from tasks where object_id in (
  select id from objects where name = '[security-check] служебный объект'
);
delete from objects where name = '[security-check] служебный объект';
commit;
```

**Что проверяется только вручную.** Через API историю удалённой задачи не видит никто, поэтому скрипт не может сам подтвердить, что она сохранилась. В конце он выводит SQL-запрос с нужным `task_id` для SQL Editor.

**Про одновременные запросы.** Проверка из 8 одновременных переходов зависит от времени выполнения запросов. Правильная функция проходит её всегда, а функция без `FOR UPDATE` проваливает её не при каждом запуске.
