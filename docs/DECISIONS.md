# Решения по вопросам, на которые ТЗ не отвечает

## Задачи

| Вопрос | Решение | Почему |
|---|---|---|
| Можно ли создать задачу без исполнителя? | Нет, `executor_id` обязателен | Без исполнителя задача никому не видна и не может двигаться дальше: первый переход делает только назначенный исполнитель |
| Можно ли сменить исполнителя? | Да, постановщик в любой момент и в любом статусе, включая «На проверке» и «Принята». Статус не меняется | Прямой ответ работодателя, см. раздел ниже |
| Что происходит с прежним исполнителем? | Он сразу теряет доступ к задаче, а новый видит всю историю, включая имя прежнего | Правило «исполнитель видит только свои задачи» действует без исключений |
| Попадает ли смена исполнителя в историю? | Нет, см. раздел ниже | По ТЗ история хранит только смены статуса |
| Можно ли редактировать задачу? | Постановщик может в любом статусе. В принятой задаче можно менять только исполнителя: название, описание и объект закрыты | Принятая работа не должна меняться задним числом. Ответ работодателя касается только исполнителя |
| Можно ли удалить задачу? | Да, постановщик в любом статусе, включая «Принята». Удаление мягкое, см. раздел ниже | ТЗ даёт постановщику право удаления без исключений |
| Обязательно ли описание? | Нет, может быть пустым | Название обязательно. Для мелких задач его достаточно |
| Кто автор задачи? | Всегда текущий пользователь (`auth.uid()`) | Клиент не может записать `author_id`: у него нет права на эту колонку |
| Нужен ли комментарий при смене статуса? | Обязателен только для «На доработке», в остальных переходах необязателен | Требование ТЗ |

## Ответы работодателя

Эти вопросы были заданы HR, ответы заменяют первоначальные решения.

**1. Смена исполнителя разрешена в любое время и в любом статусе.** Первоначально её запрещали в статусах «На проверке» и «Принята». Изменение сделано отдельной миграцией `20261105100000_allow_executor_change_any_status.sql`: уже применённые миграции не менялись. Статус при смене остаётся прежним. Менять исполнителя может только постановщик, и назначить можно только пользователя с ролью исполнителя.

**2. «При удалении задачи история тоже удаляется».** Для пользователей так и работает: удалённая задача и её история больше никому не видны через API и интерфейс, в том числе постановщику. Физически записи остаются в базе, удаление мягкое.

Это осознанное решение, а не расхождение с ответом: по ТЗ (раздел 3, п. 4) историю нельзя удалить через API. Физическое удаление задачи вместе с историей дало бы постановщику такую возможность одним запросом. Мягкое удаление выполняет оба требования: история исчезает для всех пользователей, но через API её стереть нельзя. Подробности в разделе «Почему удаление задачи мягкое».

## Почему смена исполнителя не пишется в историю

- ТЗ определяет запись истории через смену статуса: кто, когда, из какого статуса в какой, комментарий. При смене исполнителя статус не меняется, поэтому такой записи по ТЗ нет.
- Чтобы её хранить, пришлось бы либо писать в `task_history` строки с одинаковыми статусами, либо добавлять новый тип события и колонки «кто был» и «кто стал». Первое ломает проверку допустимых переходов в базе, второе добавляет функцию, которой нет в ТЗ.

**Чем это грозит.** Если исполнитель успел сменить статус, его имя останется в истории. Если он не успел ничего сделать, следов его назначения не останется. Теперь исполнителя можно сменить и у принятой задачи, поэтому в карточке может быть указан не тот человек, который выполнил работу: кто её делал, видно по истории. Если бизнесу понадобится полный аудит назначений, его стоит хранить отдельной таблицей, не меняя `task_history`.

## Почему удаление задачи мягкое

**Причина: ТЗ, раздел 3, п. 4: историю нельзя удалить через API.** При каскадном удалении один вызов API от постановщика уничтожал бы и задачу, и её историю. Формально прямого права на удаление истории нет, но по сути её можно было бы стереть через API. Поэтому:

- `tasks.deleted_at` отмечает удаление. Физически строка остаётся.
- Права `DELETE` и `TRUNCATE` на `tasks` и `task_history` нет ни у `authenticated`, ни у `anon`, ни у `service_role`.
- Удалить задачу можно только через `delete_task(p_task_id)`: это может только постановщик и в любом статусе. Функция заполняет только `deleted_at`, статус и история не меняются.
- Внешний ключ `task_history.task_id` стал `on delete restrict`: задачу с историей база не удалит физически, даже если запрос выполняет администратор.
- Удалённая задача и её история не видны никому через API, в том числе постановщику. Обе RPC отвечают «Задача не найдена», редактирование затрагивает 0 строк. Исполнитель, у которого на объекте остались только удалённые задачи, перестаёт видеть этот объект.

**Почему RPC, а не право на колонку `deleted_at`.** Политика чтения скрывает удалённые строки, поэтому обычный UPDATE, который их скрывает, столкнулся бы с проверками RLS. Кроме того, проверить роль и записать только одну колонку в одной функции проще и надёжнее.

**Граница этой защиты.** Владелец базы (`postgres` в SQL Editor) может удалить историю вручную: у него есть все права на свои таблицы. Требование ТЗ касается API, и через API это невозможно.

## Объекты

| Вопрос | Решение | Почему |
|---|---|---|
| Можно ли удалить объект с задачами? | Нет, если у него есть хотя бы одна задача, включая мягко удалённые (`on delete restrict`). Объект без задач удаляется обычным DELETE | Это проще, чем мягкое удаление объектов: не нужны новая колонка, RPC и условия в политиках, и уже работающего внешнего ключа достаточно. Каскад здесь невозможен: он удалил бы историю |
| Какое у этого последствие? | Объект, в котором когда-либо была задача, остаётся навсегда, даже если все его задачи удалены | Осознанная цена. Постановщик не видит удалённых задач, поэтому интерфейс объясняет причину отдельным сообщением |
| Что исполнитель видит в карточке объекта? | Только свои задачи | Следует из правила о чужих задачах. На одном объекте могут работать разные исполнители |

## Пользователи и доступ

| Вопрос | Решение | Почему |
|---|---|---|
| Как появляется профиль? | Его создаёт администратор (`seed.sql` или SQL). Триггера на регистрацию нет | Регистрация закрыта, а роль нельзя брать из `user_metadata` |
| Что видит пользователь без профиля? | Ничего, смена статуса тоже отклоняется | Default deny |
| Чьи профили видит исполнитель? | Свой, авторов своих задач и участников их истории | Нужны имена в карточке задачи. Полный список сотрудников ему не нужен |
| Можно ли сменить роль через API? | Нет. Администратор может через SQL, но не пока на пользователя назначены действующие задачи | Иначе `executor_id` укажет на профиль без роли исполнителя. Удалённые задачи не считаются: их нельзя снять с пользователя, и они уже никому не видны |
| Можно ли удалить пользователя с задачами или историей? | Нет (`on delete restrict`), в том числе если задачи мягко удалены | История должна оставаться достоверной |
| Что отвечает RPC на чужую задачу? | То же, что и на несуществующую: «Задача не найдена» | Исполнитель не должен узнавать, существует ли чужая задача |

## Техническая реализация

| Вопрос | Решение | Почему |
|---|---|---|
| Как создаётся задача: RPC или insert? | Обычный insert с правом только на `title`, `description`, `object_id`, `executor_id` и строгой политикой | ТЗ допускает оба варианта. Этот проще: статус и автора клиент передать не может, а запись истории добавляет триггер |
| Как триггер отличает RPC от прямого UPDATE? | По `current_user`: внутри `security definer` функции это `postgres`, при запросе через API это `authenticated` | Значение нельзя подделать из API, в отличие от настройки сессии |
| Где лежат `is_manager()` и другие помощники? | В схеме `private`, не опубликованной через API | Их нельзя вызвать как RPC даже авторизованному пользователю |
| Как работает `service_role`? | Приложение его не использует. У роли убраны `DELETE` и `TRUNCATE` на `tasks` и `task_history`, остальные стандартные права Supabase не менялись | Ключ есть только у администратора. Напрямую сменить статус или `deleted_at` не может и он: триггер пропускает только `postgres` |
| Что делает `seed.sql` при повторном запуске? | Ничего не меняет и не удаляет, если демо-данные уже есть | Скрипт не удаляет задачи и историю, поэтому не пересоздаёт и не сбрасывает демо-данные. Для чистого старта нужен новый проект Supabase |

## Интерфейс

| Вопрос | Решение | Почему |
|---|---|---|
| Откуда интерфейс знает, какие кнопки показать? | Из таблицы переходов в `src/lib/domain.ts`, копии правил из базы | Только для показа. Если таблицы разойдутся, база всё равно откажет, а интерфейс покажет её сообщение |
| Когда спрашивать комментарий? | Перед каждым переходом открывается окно с полем комментария. Для «На доработке» поле обязательно | В остальных переходах комментарий разрешён по ТЗ, значит, его должно быть где написать |
| Куда попадает пользователь после входа? | Исполнитель в «Мои задачи», постановщик в «Объекты». Постановщика с `/my-tasks` перенаправляет на объекты | В ТЗ экран «Мои задачи» предусмотрен только для исполнителя |
| Что показывать при чужой или удалённой задаче? | «Задача не найдена или у вас нет к ней доступа» | Интерфейс не различает эти случаи: база для них отвечает одинаково |
| Как закрываются диалоговые окна? | Только кнопками «Отмена» и «×» или после сохранения. Клик мимо окна и Esc его не закрывают | Случайное нажатие не должно стирать уже введённые данные |
| Как быть с устаревшей страницей? | Запрос отклоняется базой, показывается её сообщение, данные обновляются | Статус мог изменить другой пользователь. Обновлений в реальном времени в ТЗ нет |

## Что не сделано

**Осознанно, функций нет в ТЗ:**

- не хранится, кто удалил задачу: `delete_task` заполняет только `deleted_at`;
- нет корзины и восстановления удалённых задач;
- смена исполнителя не отражается в истории;
- нет постраничного вывода, поиска и фильтров в списках: при объёме тестового задания они не нужны;
- нет обновлений в реальном времени, файлов и уведомлений: прямо исключено заданием.

**Ограничения проверки:**

- `npm run check:security` проверяет API. Сохранность истории удалённой задачи через API увидеть нельзя, поэтому она проверяется запросом в SQL Editor, который выводит скрипт;
- проверка одновременных запросов зависит от времени выполнения: функция без `FOR UPDATE` проваливает её не при каждом запуске;
- автоматических тестов интерфейса в репозитории нет: задание требует проверки на уровне базы.

**Служебный объект.** После `check:security` у постановщика в списке остаётся объект `[security-check] служебный объект`. Это прямое следствие правила «объект с удалёнными задачами удалить нельзя». В README есть SQL для его удаления администратором.
